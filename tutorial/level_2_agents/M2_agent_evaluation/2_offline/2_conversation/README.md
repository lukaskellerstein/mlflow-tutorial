# L2-M2.2.2 — Offline, Conversation Scope

**Same pipeline as the turn branch. Different unit.**

```text
turn gate          case      -> agent -> turn scorers    -> threshold
conversation gate  scenario  -> agent -> SESSION scorers -> threshold
```

The dataset, the run, the score, the gate, the baseline comparison — all the
same shape. Only what counts as "one item" changes.

## Why this branch has to exist

A support agent can answer **every individual turn correctly** and still fail
the only thing the business measures: the customer did not get their problem
solved and phoned in anyway.

"Was the task ever finished?" is a property of the session. A turn gate is
structurally unable to see it, so it can report all green while the product is
failing. That is not a subtle risk — it is the normal failure mode of a
conversational agent.

## The four lessons

| # | Lesson | What it adds |
|:--|:--|:--|
| 1 | [`1_conversation_gates`](1_conversation_gates/) | Gate a ship decision on session scorers, and compare to a stored baseline |
| 2 | [`2_version_comparison`](2_version_comparison/) | Ship v2 or keep v1, where pairing works only if the user side is scripted |
| 3 | [`3_failure_analysis`](3_failure_analysis/) | The funnel: a session verdict says it failed, this says which turn broke it |
| 4 | [`4_multi_turn_benchmark`](4_multi_turn_benchmark/) | A benchmark whose unit is a conversation — the counterpart to SWE-bench and GAIA |

## The hard part: a conversation gate is not deterministic

A turn gate replays a fixed dataset, so the same candidate scores the same
twice. A conversation gate does not — the user side is generated by a model,
and every session judge is a model too.

Three ways to build a gate you can trust on top of that:

1. **Threshold on a mean** over many conversations, never on one.
2. **Run the suite k times and gate on the worst run** — pass^k. Lesson 2.
3. **Give the gate a tolerance band**, and only investigate a drop larger than
   the run-to-run spread you actually measured.

Lesson 1 does (1). Lesson 4 does (2) properly.

## What lesson 4 fixes that the single-turn benchmarks avoid

| Problem with multi-turn benchmarking | The fix |
|:--|:--|
| The conversation depends on the user simulator, which is a model | **Pin the user model in the benchmark spec**, not in the caller's config |
| Judging conversation text needs a judge, which is a model too | **Score the final state** of a database the agent had to mutate |
| One multi-turn run is luck | **Report pass^k**, not just pass@1 |

That last one is the one people skip and the one that matters most. An agent
that solves a task 3 times in 4 is not a 75% agent you can ship — it is an
agent that fails one customer in four.
