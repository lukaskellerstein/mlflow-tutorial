**Level:** AI Agents

## Overview

`1_turn/2_offline_gates` answers "is this version good enough to ship?" one
question at a time. This lesson asks the same question of a whole conversation,
and gates the ship decision on session scorers instead of turn scorers.

## Concepts

### Why a turn gate is not enough

A support agent can answer **every individual turn correctly** and still fail
the only thing the business measures: the customer did not get their problem
solved and phoned in anyway.

"Was the task ever finished?" is a property of the session. A turn gate is
structurally unable to see it, so it reports all green while the product fails.

### The pipeline is the same shape

```text
turn gate          case      -> agent -> turn scorers    -> threshold
conversation gate  scenario  -> agent -> SESSION scorers -> threshold
```

Dataset, run, score, gate, baseline comparison — identical. Only the unit
changes.

### Polarity is the trap

```python
GATES = [
    ("conversation_completeness", "min", 0.5),
    ("knowledge_retention", "min", 0.5),
    ("user_frustration", "max", 0.5),  # <- good at 0.0, not 1.0
]
```

A gate that compared every metric with `>=` would **pass the most frustrated
agent it could build**. The `op` field carries the polarity so the comparison
cannot be written the wrong way round by accident.

### A failed judge is not a zero

If a session judge cannot parse its own answer, the lesson records **nothing**
for that metric on that conversation. Scoring it `0.0` would fail the gate on a
judge bug rather than on agent quality — and a ship decision blocked by a flaky
parser is worse than no gate at all.

## Step-by-Step

### Steps 1–3: Simulate, score, gate

Each scenario is a scripted user side, so the gate itself stays reproducible.
Every turn is wrapped so the trace carries a `session_id`:

```python
@mlflow.trace(name="conversation_turn")
def run_turn(agent, history, session_id):
    mlflow.update_current_trace(session_id=session_id)
    return agent.invoke({"messages": history})
```

### Step 4: Compare against the stored baseline

The baseline is the last shipped run, found by tag rather than by a file on
disk:

```python
mlflow.search_runs(filter_string=f"tags.{BASELINE_TAG} = 'true'", ...)
```

### Step 5: Why one run is not a gate

The lesson closes by naming the thing that makes this hard. See below.

## Expected Output

```text
  [candidate] simulating 2 conversations...
    delayed_order    3 turns  conversation=1  knowledge=1  user=0
    faulty_return    3 turns  conversation=1  knowledge=1  user=0

======================================================================
  Gate report
======================================================================
  metric                          value   rule          verdict
  ---------------------------- --------   ------------  -------
  conversation_completeness        1.00   >= 0.5   PASS
  knowledge_retention              1.00   >= 0.5   PASS
  user_frustration                 0.00   <= 0.5   PASS

  VERDICT: SHIP
```

Read the `user_frustration` row against the two above it. **`0.00` is the good
outcome there**, and the rule reads `<=` while the others read `>=`. That single
difference is what a naive gate gets wrong.

On the first run there is no baseline, so the run is frozen as one. Run it again
and Step 4 compares against it:

```text
  metric                        baseline      now    delta
  ---------------------------- --------- -------- --------
  conversation_completeness         1.00     1.00    +0.00
  knowledge_retention               1.00     1.00    +0.00
  user_frustration                  0.00     0.00    +0.00
```

> [!warning]
> **A delta is not automatically a regression.** The user side is generated by a
> model and every judge is a model, so the *same* candidate scores differently
> on consecutive runs. Do not act on a small drop until you have measured your
> own run-to-run spread.

## Key Takeaways

- The gate pipeline is unchanged; only the **unit** becomes a conversation.
- Session scorers can fail a candidate that every turn scorer passes. That is
  the entire reason this lesson exists.
- **Polarity is not uniform.** `user_frustration` is good at 0.0. Carry the
  comparison operator in the gate definition, not in your head.
- A judge that failed to answer contributes nothing — never `0.0`.
- A conversation gate is **not deterministic**. Threshold on a mean over many
  conversations, run k times and gate on the worst, or set a tolerance band.
